# 四份 V1.0 文档精读与项目结构安排

**状态：** Accepted baseline

**适用范围：** WoLinkup TEL 话费充值项目

**分析依据：** 需求规格、总体架构、技术架构、详细设计四份 V1.0 正式说明书，以及现有消费者端与运营后台原型。

## 1. 项目定位

WoLinkup TEL 不是支付聚合平台，也不是泛数字商品平台。它是面向全球话费充值的业务系统，聚合国家、地区、运营商、充值商品与供应商网络，为国际站和中国大陆站提供统一的报价、下单、支付衔接、履约、售后、财务与运营闭环。

当前范围只包含手机话费充值。eSIM、流量包等数字商品不进入 TEL V1.0。国际站与中国大陆站复用同一套核心领域和供应商网络，但拥有独立的 UI、内容、商品上架、支付方式展示与合规策略。

## 2. 系统边界

TEL 内部负责：

- 客户与收件号码、站点与渠道、目录与商品、定价与报价。
- 订单、供应商采购、充值履约、退款业务、风险审查。
- 业务财务事实、供应商预存款、对账差异、运营和审计。
- 支付平台与供应商的防腐层、回调接收、状态投影和异常恢复。

独立 WoLinkup Payment Platform 负责：

- 收银台、支付方式、支付服务商、商户号和支付路由。
- 支付机构回调、支付状态权威记录、支付侧退款执行与结算。
- 真实支付凭证和支付机构 SDK。

TEL 只能保存支付平台业务引用、标准化状态投影和审计证据。仓库中不得引入支付机构 SDK、真实商户配置、收银台实现或生产支付密钥。

## 3. 业务全链路

1. 用户选择站点、国家/地区、运营商、目标号码和充值商品。
2. 服务端验证号码与商品可售性，结合站点、币种、费用和有效期生成一次性报价。
3. 报价、订单和幂等键在同一事务内消费与固化，订单进入待支付状态。
4. TEL 请求支付平台创建支付会话；客户端只与支付平台完成支付交互。
5. TEL 接收经过验签和去重的标准支付事件，并主动查询支付平台处理中断恢复。
6. 只有明确支付成功且通过风险门控的订单，才能释放到履约队列。
7. 路由选择已批准的主供应商或备选供应商；首期为人工配置的静态规则。
8. worker 通过供应商适配器提交充值、查询原请求、处理回调并收敛最终结果。
9. 成功后形成订单、履约和财务事实；失败或未知状态进入售后与人工处置。
10. 退款先申请、审批和预占退款额度，再调用支付平台执行；对账持续核对内部事实、支付平台和供应商结果。

## 4. 必须由代码和数据库共同守住的业务不变量

- 报价由服务端生成、具有过期时间且只能按规则消费一次。
- 支付成功不等于充值成功；`PROCESSING` 或 `UNKNOWN` 不得触发充值。
- 同一订单最多存在一个未解决的履约尝试，`SUBMITTING` 也计入未解决。
- 供应商结果未知时只能查询原请求，不得盲目重提或切换供应商。
- 退款审批后先预占可退额度；退款 `UNKNOWN` 时不能释放该额度。
- 供应商预存款“已发起”不增加可用余额，只有确认到账才增加。
- 外部副作用必须可幂等、可追踪、可恢复；关键事件必须持久化。
- 金额采用十进制定点值和 ISO 4217 币种，不使用浮点数计算交易金额。

## 5. 领域划分

| 代码 | TEL 模块      | 核心所有权                                   |
| ---- | ------------- | -------------------------------------------- |
| D01  | `customer`    | 消费者身份、收件号码与偏好                   |
| D02  | `site`        | 站点、渠道、语言、币种与内容策略             |
| D03  | `marketing`   | 优惠、活动和权益；首期后增强                 |
| D04  | `catalog`     | 国家、运营商、产品、面值和可售目录           |
| D05  | `pricing`     | 价格、汇率、费用、报价与报价快照             |
| D06  | `procurement` | 供应商、供应商品、采购成本、路由配置与预存款 |
| D07  | `fulfillment` | 充值尝试、提交、查询、回调与异常恢复         |
| D08  | `order`       | 充值订单、订单状态和售后入口                 |
| D10  | `finance`     | 业务财务事实、退款业务、对账与结算投影       |
| D11  | `risk`        | 规则、风险决策、人工审核和风控证据           |
| D12  | `foundation`  | 国家、币种、时区、审计、幂等和平台事件基础   |

D09 支付是外部独立平台，不建立 TEL 内部支付领域模块；`integrations/payment-platform` 只是防腐层。

## 6. 状态模型基线

- `TopupOrder`：`PENDING_PAYMENT`、`PAYMENT_PENDING`、`PAID_PENDING_REVIEW`、`PAYMENT_EXCEPTION`、`PAID_READY_FOR_FULFILLMENT`、`FULFILLING`、`COMPLETED`、`FAILED_FOR_AFTERCARE`、`CANCELLED`。
- `PaymentProjection`：`PENDING`、`PROCESSING`、`SUCCEEDED`、`FAILED`、`CANCELLED`、`UNKNOWN`。
- `FulfillmentAttempt`：`PENDING`、`SUBMITTING`、`SUBMITTED`、`PROCESSING`、`SUCCEEDED`、`FAILED_FINAL`、`RESULT_UNKNOWN`。
- `RefundOrder`：`REQUESTED`、`REVIEWING`、`APPROVED`、`PROCESSING`、`SUCCEEDED`、`FAILED`、`UNKNOWN`、`REJECTED`。

这些状态属于不同聚合，不能压缩成一个“订单状态”。每个迁移必须有触发条件、幂等键、审计证据和允许的补偿动作。

## 7. 产品与接口视图

消费者核心路径为：`/reference`、`/catalog/topups`、`/quotes`、`/orders`、`/orders/{id}/payment-session`、订单查询、常用号码和退款申请。运营后台覆盖订单、支付投影、履约、供应商、目录、定价、财务、退款、对账、风险、内容和审计。

API 使用 REST 与 OpenAPI 3.1.1，统一前缀 `/api/v1`。消费者身份与运营身份分离；后台授权必须由服务端执行，敏感操作需要原因、审批或双人复核。机器契约只有在完成接口评审后才能成为权威文件，当前目录仅建立承载位置。

## 8. 技术与部署基线

- Node.js 24 LTS、TypeScript 6、NestJS 11、Next.js 16、React 19、pnpm 11。
- PostgreSQL 18；Kysely 执行 SQL，Zod 负责边界校验。
- 同进程非关键通知可用本地事件总线；关键或跨进程任务使用 Outbox/Inbox 与 pg-boss。
- Pino 日志、OpenTelemetry 追踪，Vitest 单元/集成测试，Playwright 端到端测试。
- 首期使用 Caddy、Docker Compose、单云主机和托管 PostgreSQL。
- 首期不引入 Redis、BullMQ、Kafka/RabbitMQ、Kubernetes、服务网格或按领域拆分的微服务。

上述约束是首期复杂度预算，不妨碍以后在明确的容量、团队或隔离需求出现时通过 ADR 演进。

## 9. 分期范围

| P0   | 双站核心充值、支付平台集成、人工批准的主备路由、订单与履约事实、供应商预存款、退款和基础对账 |

## 10. 结构决策

正式结构将“运行单元、领域所有权、外部集成、共享契约、数据、测试、工具和部署”分开。模块内部后续统一采用：

```text
module/
  domain/          聚合、实体、值对象、领域规则
  application/     用例、命令、查询、事务边界
  ports/           仓储和外部能力接口
  infrastructure/  PostgreSQL、消息和端口实现
  api/             模块公开 facade 与 DTO
  tests/           模块内测试
```

跨模块只能使用公开 facade、DTO 或已发布事件，不能直接读取别的模块表或导入内部实现。首期模块在 `tel-api` 和 `tel-worker` 进程内组合，目录边界不等于部署边界。

## 11. 旧脚手架处理

早期结构包含内部支付财务服务、Redis/BullMQ、Turborepo、动态供应商路由以及与正式状态机不同的契约。直接继续开发会形成双重真相，因此原样移动到 `archive/initial-scaffold`，不参与工作区、构建、校验和部署。它只用于追溯早期思路；任何可复用代码必须按当前契约重新评审后迁移，禁止整包恢复。

## 12. 数据迁移序列

迁移文件按正式详细设计逐步建设：`0000_platform_events`、`0001_foundation_reference`、`0002_customer_site`、`0003_catalog_supplier`、`0004_pricing_quote`、`0005_topup_order`、`0006_payment_integration`、`0007_fulfillment`、`0008_finance_settlement`、`0009_refund_service`、`0010_risk`、`0012_constraints_indexes`。

当前只创建目录与顺序说明，不把旧数据库脚本冒充为正式迁移。

## 13. 待确认事项

- 首批上线国家、运营商、供应商与站点语言。
- 支付平台的版本化接口、签名、认证、超时、重放和退款契约。
- 各供应商是否支持请求幂等、原单查询、回调和明确的终态语义。
- 峰值容量、数据库连接预算、RTO/RPO 和备份保留周期。
- 法律实体、数据驻留区域、跨境数据与消费者身份模型。
- 钱包是否满足准入条件，以及价格、汇率、税费和合规规则的最终口径。

这些事项必须进入 ADR、需求变更或契约评审，不能由开发默认猜测。

## 14. 推荐实施顺序

1. 固化术语、状态机、金额模型、幂等与审计规范。
2. 建立 OpenAPI、事件 schema、支付平台契约和供应商 SPI 的机器契约。
3. 建立 PostgreSQL 迁移、领域约束、Outbox/Inbox 和 pg-boss 基础设施。
4. 打通报价到订单、支付成功门控、单次履约和结果查询的最小闭环。
5. 补齐退款预算、供应商预存款、三方对账和人工异常工作台。
6. 接入双消费者站和运营后台，再以恢复、安全和契约测试作为上线准入。
